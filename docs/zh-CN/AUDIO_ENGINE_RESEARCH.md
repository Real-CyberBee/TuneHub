# TuneHub 开源音乐引擎调研

> 调研日期：2026-09-25
>
> 范围：面向 TuneHub 当前浏览器端事件生成器，寻找能改善音色表达或简化音频适配的开源方案。本文依据项目代码和候选项目的一手资料整理；未做听感盲测或性能基准。

## 结论摘要

**没有一个引擎能同时解决“更好听”“更易开发”“离线可复现”这三件事。** TuneHub 已拥有一套可实时播放与离线渲染的 Web Audio 实现；现阶段最明显的不足不是总音量包络，而是大多数有音高的音色仍由基础波形合成，缺少可直接使用的高质量真实乐器音源或通用物理建模音源。

建议保留生成内核、事件格式和现有原生 Web Audio 适配器，分两条路径验证：

1. 若目标是增加钢琴、弦乐等更接近真实乐器的声音，先试 **smplr**，作为可选采样器适配器接入；在随产品分发或托管音源前，逐个核对样本文件的许可、来源和缓存/离线策略。
2. 若目标是制作 TuneHub 自有的合成器或物理建模音色，再评估 **FaustWasm**；它是 DSP 开发与执行环境，不是现成音色库，工程与许可证成本更高。
3. **Tone.js** 的优势是合成器、效果器与调度 API 更完整，适合减少手写 Web Audio 节点代码；它不会自动带来真实乐器音色，而 TuneHub 已有自己的调度和离线导出路径，因此不建议仅为“音质”整体替换。

## 当前实现与需求界定

仓库实现并非单一持续正弦波配总包络收尾：

- [音频引擎](../../src/audio/engine.mjs) 定义了多振荡器音色配方、声部包络与滤波、噪声打击乐、确定性混响，以及手碟的并行模态共振。
- [导出适配器](../../src/audio/export.mjs) 通过 `OfflineAudioContext` 复用 `playNoteOn` 进行离线渲染。
- 因此更准确的待解决问题是**常规有音高音色的声源种类和细节有限**。换一个节点封装库可能改善开发体验，但若没有采样素材或更复杂的 DSP 算法，并不等于音色自然度会提升。

## 候选方案比较

| 方案 | 提供什么 | 对 TuneHub 的潜在收益 | 主要代价 / 局限 | 判断 |
|---|---|---|---|---|
| **原生 Web Audio（现状）** | 浏览器标准音频图、振荡器、滤波、增益、缓冲区与离线上下文 | 无运行时依赖；对现有确定性事件流、种子化噪声与离线渲染控制直接 | 更复杂的合成器、包络调制、复音管理和效果路由需要自己维护 | 保留为默认/基线适配器 |
| **Tone.js**（MIT） | Web Audio 音乐框架；含多种合成器、采样器、效果器、Transport 等高层 API | 减少手写节点与调度代码；能用 FM/AM/噪声等合成方式扩展音色 | 其基本合成器依然是合成器；真实乐器仍需采样文件。替换会重做适配层；需要验证与现有离线确定性路径的兼容和维护方式 | 适合具体 API/开发效率痛点，不作为音质升级的单独方案 |
| **smplr**（MIT） | Web Audio 采样乐器集合，提供采样器、若干乐器/鼓组、SoundFont 读取能力和 `OfflineAudioContext` WAV 渲染 API | 最直接地给事件流增加采样音色；示例覆盖钢琴、多层力度钢琴、打击乐等 | 项目文档说明默认样本从网络加载；需要处理样本许可、托管/缓存、预加载与断网体验。MIT 代码许可不自动涵盖独立样本 | 建议优先做小范围可选适配器原型 |
| **FaustWasm**（LGPL-2.1-or-later，见其许可证文本） | Faust DSP 编译为 WASM，并包装为 Web Audio 节点；可生成乐器/效果节点，项目说明支持离线渲染 | 可编写专属振荡器、滤波器、延迟线、物理建模等定制 DSP；适合需要超出现成 Web Audio 节点的声音 | 不是预制音色库；需要 Faust/DSP 技能、编译与 WASM 发布流程，并评估 LGPL 义务、浏览器兼容和离线渲染行为 | 仅在明确需要自研 DSP/物理模型后评估 |

## 物理建模发声是否可行

**可行，且有可直接复用的开源模型。** Faust 官方 `physmodels.lib` 列出了开弦/吉他、弓弦/小提琴、簧片/单簧管、铜管、长笛，以及 djembe、木琴和钟等模型。FaustWasm 可以把 Faust DSP 编译为 WASM，并把生成的 DSP 暴露成 Web Audio 节点，因此可以作为浏览器内物理建模原型的候选路径。

要区分两类“物理仿真”：

- **实时物理建模合成**：以波导、振动模态、反馈网络等简化模型，模拟激励、振动和共鸣之间的关系。通过琴弦长度/张力、阻尼、拾音位置、吹气/弓压等参数控制声音，适合交互演奏和实时生成。Faust `physmodels.lib` 属于这一类；TuneHub 现有手碟代码中的多模态共振也属于较轻量的模态近似。
- **高精度结构/材料声学仿真**：从乐器几何、材料参数和边界条件出发，使用有限差分/有限元等数值方法求解振动与声场，再合成或卷积输出。它更接近用户所说的“材料学仿真”，但通常需要几何模型、参数测量、数值求解和验证；不能仅靠换一个 Web 音频库获得，也更难直接满足移动浏览器的实时预算。

因此，现成的实时物理建模不是“每种木材/金属的精确数字孪生”。它能提供比单纯振荡器更有因果感的音色变化，但自然度取决于模型覆盖了多少真实发声机制，以及参数是否经过测量和校准。若目标是可演奏的物理乐器音色，可从 Faust 的弦乐或模态打击乐模型试起；若目标是特定真实乐器的高保真还原，录制采样往往是更便宜、更可靠的基线。

## 主要风险与技术约束

### 1. 采样音源与代码许可是两件事

smplr 仓库标注代码为 MIT，但其 README 指出示例音色样本由独立仓库托管，且默认通过网络加载。应对**每套音源及其每个样本来源**单独确认许可是否允许产品使用、复制和再分发。若暂时无法确认，可先做开发期原型、使用自备且许可明确的样本，或允许用户加载自有音源；不要把库的 MIT 标记视作所有样本均可商用。

### 2. 离线渲染与网络加载需要明确策略

TuneHub 的分享与导出强调确定性。采样方案要确认同一音源版本、同一事件是否能稳定离线渲染；样本加载失败时是否等待或回退；导出是否复用已解码缓存；分享链接是否应记录音源 ID/版本。FaustWasm 和 Tone.js 的 API 也需在目标浏览器上与现有实时、区间及全曲离线路径逐一验证，文档功能声明本身不能代替集成验证。

### 3. 不把引擎替换误当作音色设计

Tone.js 提供的合成器与效果器可改善表达能力和开发效率，但声音差异仍取决于 patch、调制、滤波、包络、空间处理及素材。对 TuneHub 的核心问题，听感对比应固定乐句与响度，对比“当前振荡器 patch”“采样音源”“定制 DSP”，避免只比较 API 表面。

## 建议的评估路径

1. 继续使用现有 `NoteEvent` 和音频适配器边界，不让外部引擎进入纯生成内核。
2. 选 2–3 种明确缺失的声音（例如钢琴、拨弦、弦乐铺底），用 smplr 或授权清晰的自有样本实现一个可关闭的适配器；并保留当前音色作为回退。
3. 同一段固定种子、同一 MIDI/音高事件、匹配响度，进行主观试听；同时检查加载时间、离线 WAV、区间导出、无网络行为和连续播放边界。
4. 若采样方案不能覆盖目标（例如需要无限音高可变、可解释的微分音合成或物理交互），再建立单独的 FaustWasm DSP 原型。此阶段再评估 WASM 体积、CPU 与许可证合规。
5. 只有当现有的调度、复音管理或效果器维护确实拖慢迭代时，才针对性试用 Tone.js；可先替换一个声部或效果链，不做全量迁移。

## 调研限制

这次调研比较了官方公开能力和许可证，未安装候选依赖、未验证当前版本浏览器兼容、性能、bundle 体积、不同离线输出的一致性，也未做听感盲测。建议把最终选型建立在固定种子样例试听和目标浏览器导出验证上，而非仅凭项目描述判断音质。
