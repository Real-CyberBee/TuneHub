## 0. 一句话结论

**不要从零造音频引擎，也不要直接套用现成的"音乐 App"。**
正确的形状是：**自研一个薄而深的核心（种子化事件流 + 可组合约束），把合成、律制、可视化、导出都做成可替换的外围适配器**，并优先复用 MIT 许可的成熟库。

调研后最关键的三个判断：

| 判断 | 结论 | 依据 |
|---|---|---|
| 引擎选型 | 用 **Tone.js** 做音频底座，**自研**约束/生成内核 | Tone.js 是 MIT、v15 活跃、且已内含 `standardized-audio-context`；但它不理解"约束"与"律制"，那正是我们的差异化所在 |
| 律制选型 | 用 **sonic-weave**（MIT）+ **Scala `.scl`** 作为音高数据层 | 它把"频率/比例/等分"做成了带 TypeScript 类型的 DSL 与 npm 包，直接可用；`.scl` 是世界通用交换格式 |
| 最大风险 | **不是技术，是许可证污染 + 世界音乐的"近似"诚实度** | SuperCollider/Sonic Pi 是 GPL、Essentia.js 是 AGPL；甘美兰/拉格无法被音阶数据完整表达 |

## 1. 从 demo 读出的架构教训

原始 demo（`prototype/original-demo.html`）有 3 个必须修掉的结构性问题，它们直接决定了架构：

**问题 1：随机数直接内联在业务逻辑里。**
`Math.random()` 出现在 `triggerEvents()` 中，没有可注入的种子源。这导致"保存随机种子"这个需求**在现有结构下无法实现**——你无法重放一段已经消失的随机序列。

> 修正：内核中**禁止出现裸 `Math.random()`**，全部经由注入的 PRNG（如 mulberry32/xorshift128）。种子是唯一随机真源。

**问题 2：`setTimeout` 参与发声调度。**
`playNote()` 用 `setTimeout(..., cfg.decay*1000)` 回收声部计数。这在实时播放时勉强能用，但**离线渲染（`OfflineAudioContext`）中会彻底崩坏**——离线上下文里时间飞逝，`setTimeout` 与音频时钟脱钩，限流逻辑会失效。

> 修正：所有调度与状态回收必须基于 `AudioContext.currentTime` 的时间轴，用一个**前瞻调度器（look-ahead scheduler）** 统一驱动。这是离线渲染与实时播放共享同一份代码的前提。

**问题 3：约束逻辑与发声逻辑耦合。**
`triggerEvents()` 里 `if (state.mode === 'raw') {...} else {...}` 把"音高量化、限流、音量归一"三件事糊在一起，靠一个 mode 字符串切换。

> 修正：约束应当是**独立的纯函数层**，输入输出都是事件对象。`mode` 只是"一组预设约束"的别名。

**保留的优点**：`quantizePitchToPentatonic()` 这个函数虽然简单，但它就是整个项目的原型——**它做的事是"把一个连续/离散空间投影到一个音乐上有意义的子空间"**。音高量化是最简单的一种；扩展到时间量化、和声约束、律制映射、拉格语法，就是完整的 TuneHub。

## 2. 核心架构提议

```
┌─────────────────────────────────────────────────────────────┐
│  表现层 Presentation                                          │
│  可视化(§5) · 控件 · 分享/URL · 无障碍                        │
└──────────────────────────┬──────────────────────────────────┘
                           │ 事件流 / 状态快照
┌──────────────────────────▼──────────────────────────────────┐
│  内核 Kernel（自研，薄而深，无 DOM 无 WebAudio 依赖）          │
│                                                              │
│  ┌────────────┐   ┌──────────────┐   ┌──────────────────┐   │
│  │ PRNG       │──▶│ Generator    │──▶│ Constraint Chain │   │
│  │ (seed)     │   │ 生成原始事件  │   │ 纯函数算子序列     │   │
│  └────────────┘   └──────────────┘   └────────┬─────────┘   │
│                                                │             │
│                          ┌─────────────────────▼──────────┐  │

│                          │ (音频时钟驱动, 实时/离线同构)     │  │
│                          └─────────────────────┬──────────┘  │
└────────────────────────────────────────────────┼─────────────┘
                                                 │ NoteEvent[]
┌────────────────────────────────────────────────▼─────────────┐
│  适配器层 Adapters（可替换）                                   │

│  Viz: Canvas2D │ WebGL/three │ 记谱(VexFlow) │ 外部窗口       │
│  Export: WAV │ MP3 │ Opus │ MIDI │ 分享码                     │
└──────────────────────────────────────────────────────────────┘

### 2.1 内核数据结构（草案）

```ts
type Seed = number;                       // 32-bit，可编码进 URL

interface NoteEvent {
  readonly time: number;    // 秒，相对作品起点（非墙钟！）
  readonly duration: number;
  readonly voice: VoiceId;
  readonly pitch: Pitch;    // 音高对象，见下
  readonly velocity: number;
  readonly tags?: ReadonlySet<string>;  // dropped/scheduled/accent 等，供可视化
}

// 音高不是 MIDI 整数——这是与世界音乐对接的关键抽象
type Pitch =
  | { kind: 'ratio';    readonly num: number; readonly den: number; readonly ref: number } // 纯律 3/2
  | { kind: 'cents';    readonly cents: number; readonly ref: number }                     // 任意微分音
  | { kind: 'edo';      readonly step: number; readonly divisions: number; readonly ref: number } // n-EDO 第 k 步
  | { kind: 'absolute'; readonly hz: number };                                             // 甘美兰实测频率
```

> **设计要点**：`Pitch` 是带标签联合而非 MIDI 数字。MIDI 数字是 12-TET 的编码，一旦把音高退化成正整数，就永久失去了表达中立三度、甘美兰、纯律比例的能力。UI 层可以把它显示成 MIDI 音符号，但内核不能。

```ts
// 约束算子：纯函数，可组合，可序列化
type Constraint = (events: readonly NoteEvent[], ctx: GenContext) => readonly NoteEvent[];
```

### 2.2 为什么"薄而深"

内核不 import Tone.js、不碰 canvas、不知道什么是 BPM 输入框。它的全部职责是：**给定 (种子, 配置) → 确定性地产出一个 NoteEvent 序列**。

这样做的收益是决定性的：
- **离线导出**：同一个内核跑在 `OfflineAudioContext` 上，直接渲染成音频，无需"录屏式"捕获。
- **可测试**：纯函数，快照测试即可覆盖。
- **可分享**：`(种子, 配置)` 就是作品的全部——序列化成 8–64 字符的分享码。
- **可回溯**：UI 上的每一次参数改动都能重放。

## 3. 六项需求的落地方案

### 需求 1：收集各种音效的 WebAudio 合成

**分层策略**，从"零依赖"到"重量级"：

| 层 | 技术 | 用途 | 依赖 |
|---|---|---|---|
| L1 | 原生振荡器/噪声/包络 | 打击、贝斯、基础音色 | 无 |
| L2 | FM/PM、波表（`PeriodicWave`）、加法 | 钟声、电钢、金属感 | 无 |
| L3 | 滤波 + `WaveShaper` + `Convolver`（IR 混响） | 失真、空间感 | 无（IR 需自备） |
| L4 | 物理建模（Karplus-Strong、模态合成） | 拨弦、鼓皮、木石 | AudioWorklet |
| L5 | 采样器 / SoundFont | 真实乐器 | `smplr`（MIT，v1.0，已核实） |
| L6 | WASM DSP（Faust/Csound） | 复杂/实验音色 | 可选，重量级 |

**建议**：L1–L3 覆盖 80% 需求且零依赖，先做；L5 用 `smplr` 补真实乐器；L4 用 AudioWorklet 手写几个标志性音色（Karplus-Strong 是性价比之王）；L6 留作可插拔的高级功能。

详见 `03-synthesis-viz-export.md`。

### 需求 2：随机音乐生成 + 更多自定义空间与音乐化算法

把 demo 的"两种模式"升级为**四层算法栈**：

| 层 | 算法族 | 例子 |
|---|---|---|
| **生成层** | 随机过程 | 均匀/加权随机、马尔可夫链、L-System、元胞自动机、混沌映射（logistic）、语法制导生成、约束满足（CSP） |
| **约束层** | 音乐化算子 | 音高量化、时间栅格化、声部限流、力度归一、音域折叠、和声一致性检查、动机重复/变奏 |
| **结构层** | 曲式 | 段落（intro/A/B/outro）、张力曲线、密度包络、织体切换、渐变过渡 |
| **演化层** | 长时程 | 调式漂移、律制游移、节奏加速/减速、声部进退场 |

**关键**：生成层必须能输出"未音乐化"的结果（保留 demo 的 raw 模式），因为**对比本身就是最好的教学**——用户按一个按钮听到"约束前 → 约束后"，比任何文字都更能说明"什么是音乐"。

参考实现生态：Strudel（MIT，TidalCycles 的 JS 移植）、Tone.js（MIT）、Orca（MIT）、Gibber、Magenta.js（Apache-2.0，但已不活跃）。详见 `01-engines-generative.md`。

### 需求 3：集成各种音乐体系（本文档的重点）

用户列出的 8–10 类律制家族是正确的，但**它们不是同一层的东西**，混在一起会做出错误的抽象。建议拆成**三个正交层**：

```
律制层 Tuning      —— 频率如何生成（等分/比例/实测）
音阶层 Scale       —— 从律制中取出哪些音级
框架层 Framework   —— 这些音级如何被使用（上行下行/重点音/惯用乐句/即兴规则）
```

**为什么必须拆开？** 因为印度拉格和阿拉伯木卡姆不属于"音阶"层——它们规定的是**行为**。把拉格塞进"音阶"数据结构里，就永远做不出能听的拉格生成器。同理，甘美兰的斯连德罗/佩洛格不是 12-TET 上的音阶，而是**每套合奏实测的一组频率**，必须用 `Pitch.kind === 'absolute'` 承载。

| 家族 | 律制层 | 音阶层 | 框架层 | 可实现度 |
|---|---|---|---|---|
| 五度相生/毕达哥拉斯 | 3:2 叠置 | 由叠置导出 | — | ✅ 精确 |
| 纯律 | 简单整数比 | 从比例集合选 | — | ✅ 精确 |
| 中庸律/历史律制 | 音 comma 分割 | 键盘映射 | — | ✅ 精确 |
| 十二平均律 | 12-EDO | 任何 12 音子集 | 大小调功能 | ✅ 精确 |
| 其他等分八度 | n-EDO (7/19/24/31/53) | n 音子集 | — | ✅ 精确 |
| 微分音/中立音 | 24-TET 或比例 | 中立三度/七度 | 木卡姆（部分） | ⚠️ 理论 vs 实践有差 |
| 非等分合奏调音 | **实测频率** | 斯连德罗/佩洛格 | pathet | ⚠️ 每套不同，需实测数据 |
| 五声/七声自然音 | 多为 12-TET 或纯律 | 宫商角徵羽/都节/琉球 | 调式功能 | ✅ 良好 |
| 调式—旋律框架 | 各式 | — | **拉格/木卡姆/达斯特加赫** | ⚠️ 需要行为数据，非音高数据 |
| 口传/非固定音高 | 无固定律制 | 无 | 滑音/腔化/泛音 | ❌ 只能做"致敬式"近似 |

> **诚实说明**：上表最后一行与两个 ⚠️ 是本项目的学术诚信红线。做出"蒙古呼麦生成器"却只会按音阶发正弦波，是对该传统的冒犯。建议对这类体系采用**不同的产品形态**：不是"生成一段呼麦"，而是"提供泛音列交互工具，让用户自己唱/吹"。

**直接可用的开源资源**（详见 `02`）：
- **sonic-weave**（MIT，v0.14.1，已核实）：微调 DSL + TypeScript npm 包，支持 `tet(n)`、比例运算、音 comma 消解，是 Scale Workshop 3 的语言内核。
- **Scala `.scl`/`.kbm` 格式**：事实标准，Huygens-Fokker 归档有数千个音阶文件。
- **Scale Workshop**：浏览器微调工具，可参考其交互设计。
- **Apotome & Leimma**（Khyam Allami/Counterpoint）：阿拉伯/中立音体系的浏览器工具，交互范式值得学习。
- **CompMusic / Saraga**（印度音乐语料）、**Dunya**（土耳其木卡姆语料）：学术数据集，**多为研究用途许可，需逐个确认**，不可默认商用或再分发。

### 需求 4：丰富的可视化

音乐的视觉化有**五个正交维度**，建议做成可自由组合的"可视化矩阵"而非固定几种视图：

| 维度 | 表示 | 实现 |
|---|---|---|
| 音高（纵） | 钢琴卷帘、五线谱、**音高螺旋/螺旋阵列**、Tonnetz、五度圈、音分偏差图 | Canvas2D / SVG / VexFlow |
| 时间（横） | 时间轴、波形、频谱图（spectrogram） | Canvas2D + `AnalyserNode` |
| 音色/能量 | 频谱条、Mel 谱、色度（chroma）、响度包络 | `AnalyserNode` / 自研 FFT |
| 空间/声部 | 声部泳道、粒子、3D 声场 | WebGL / three.js |
| 抽象/氛围 | 谐波轨迹（harmonograph）、Lissajous、粒子系统 | WebGL / regl |

**最有项目特色的两个**：
1. **音分偏差表（cent-deviation）** —— 实时显示每个音相对 12-TET 的偏离。这是让用户"看见"不同律制差异的最直观方式，也是本项目的招牌可视化。
2. **螺旋阵列 / Tonnetz** —— 把和声关系画成几何，非音乐人能立刻看到"距离"。

**技术选型**：优先 Canvas2D（音符密度高时性能最好，且 demo 已证明可行）；需要粒子/3D 时用 WebGL；记谱用 VexFlow。
**许可证警告**：`butterchurn`（Milkdrop 移植）为 GPL——可作可选外部模块，不可静态链接进 MIT 内核。详见 `04-licensing.md`。

### 需求 5：用户友好的 WEB 前端

四项具体需求的技术方案：

**① 保存/加载随机种子**
内核已保证确定性。种子编码进 URL（如 `#s=7f3a91c2&c=...`），配一个"分享"按钮。这是最便宜也最强大的分享机制——**URL 就是作品**。
同时提供"种子 + 配置"的完整快照（JSON），支持导入导出。

**② 截断某一段时间并保存 —— 这是最需要设计决策的一项**

有两条路，各有致命权衡：

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **实时捕获** | 输出接 `MediaStreamDestination` + `MediaRecorder` | 实现简单，能录"当前正在响的" | 只能录已经过去的、无法预知；时长不可控；音质受实时影响；后台标签页会被节流 |
| **离线重渲染（推荐）** | 用 `OfflineAudioContext` 从种子重跑指定时间段 | 精确区间、任意时长、快于实时、音质稳定、可确定性复现 | 需要内核支持"从任意时间点起算"（即调度器必须能在 t 起点冷启动） |

> **推荐方案**：以**离线重渲染为主**，实时捕获作为"没时间想，先录下来"的兜底。
> 这决定了内核的一个硬性要求：**调度器必须能在不播放的情况下，仅凭 (种子, 配置, 起始时间, 时长) 生成事件**。这正是 §1 问题 2（`setTimeout` 调度）必须修掉的深层原因。

**③ 导出音频**：WAV（自研编码，零依赖）→ MP3（`lamejs` 系）→ Opus（WASM）。MIDI 导出用 `@tonejs/midi`，注意**微分音 MIDI 需借 pitch bend 或 MTS**，标准 MIDI 文件无法直接表达非 12-TET。

**④ 零基础可用性**：三个层级 —— 「按一下就出声」的预设卡片 → 「调四个滑块」的简易模式 → 「打开算子面板」的专业模式。

### 需求 6：上线为网站，分享交流

架构上预留：
- 作品 = 种子 + 配置（小到能进 URL，无需后端即可分享）
- 需要社区时再加后端：作品存储、评论、fork、排行榜
- **版权提醒**：用户生成内容的授权条款、以及"AI/算法生成内容"的版权归属，需在服务条款中明确。若引入 ML 模型，还需注意模型权重自身的许可证（部分音乐生成模型为**非商用**许可）。

## 6. 待决策问题（需要你拍板）

1. **许可证路线**：项目用 MIT 还是 Apache-2.0？这决定了能否链接 GPL 组件，是**所有后续架构决策的前置**。
2. **音源哲学**：优先"合成音色"（实验感强、零资源）还是"采样真实乐器"（好听、需资源与带宽）？建议前者为主、后者可选。
3. **ML 模型的角色**：是否引入神经网络生成（MusicGen 等）？若要，**模型权重许可**需单独审查，且浏览器端需 ONNX/WASM，成本较高。建议**先不做**，把确定性算法做扎实。
4. **世界音乐的深度目标**：是"让用户能听到并对比不同律制"（可达、诚实），还是"生成风格可信的甘美兰/拉格"（需要实测数据与乐理专家，且部分目标不现实）？**强烈建议选前者**，并对后者明确划出"不做"的边界。
5. **后端何时入场**：能否接受前 4 个里程碑完全纯前端、无服务器？

## 7. 明确"不做"的清单

诚实地划出边界，比承诺一切更能建立信任：

- ❌ 不声称能生成"正宗"的甘美兰/拉格/木卡姆——只提供律制与框架的**工具**，音乐性由用户决定
- ❌ 不表达任何口传传统的"权威版本"——呼麦、喉音、原住民音乐不做音阶化处理
- ❌ 不在第一期做多用户实时协作
- ❌ 不承诺 AI 生成内容的版权归属（法律灰色地带，交由用户协议处理）
