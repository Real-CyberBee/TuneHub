# 04 · 许可证矩阵与架构约束

> **本文应当最先读**。许可证不是法律流程，而是**架构的硬约束**——它决定哪些模块能链接、哪些必须隔离。
> ⚠️ 本文中的许可证信息部分来自本轮网络核实的 npm registry 数据，部分来自既有知识。
> **未核实项均已标注 `⚠️ 待核实`，实施前必须逐个确认官方仓库的 LICENSE 文件。** 详见 `99-verification-notes.md`。

---

## 1. 为什么许可证决定架构

开源许可证分三档，对本项目的影响完全不同：

| 档位 | 常见许可 | 能否链接进 MIT/Apache 项目 | 后果 |
|---|---|---|---|
| **宽松 (Permissive)** | MIT, Apache-2.0, BSD, ISC | ✅ 可以 | 保留版权声明即可。**首选** |
| **弱传染 (Weak copyleft)** | LGPL, MPL | ⚠️ 动态链接/未修改可，静态链接需谨慎 | 需保持模块边界清晰、允许替换 |
| **强传染 (Strong copyleft)** | GPL, AGPL | ❌ 不可链接 | 会让整个项目变成 GPL/AGPL |

### AGPL 对 Web 项目的特殊杀伤力

**AGPL 的"网络条款"规定：通过网络提供服务也算分发。**
这意味着：如果一个 AGPL 库被加载到浏览器端代码里，**你的整个网站可能被要求开源**。
对"将来上线为网站"的目标（需求 6）来说，AGPL 是**最高级别的风险**。

> **关键架构结论**：本项目**完全可以在纯宽松许可的依赖集合下实现全部核心功能**。

> **不要为了一时的便利引入 AGPL/GPL 依赖**——将来上线网站时，这会变成"要么全站开源，要么重写"的绝境。

## 4. 数据与内容的许可证（常被忽视）

**代码许可证 ≠ 数据许可证**。这是最容易踩坑的地方。

| 资源 | 许可风险 | 处理方式 |
|---|---|---|
| **Huygens-Fokker Scala 归档**（数千 .scl） | ⚠️ 免费下载 ≠ 可再分发 | **只提供解析器，不打包音阶文件**；提供官方下载链接 |
| **Xenharmonic Wiki** | ⚠️ 通常 CC BY-SA（**传染性**） | 文字内容与代码严格分离；引用需署名 + 相同方式共享 |
| **CompMusic / Saraga / Dunya** | ⚠️ **研究用途，禁止商用/再分发** | 只引用论文中的**测量数值**并注明出处；不分发音频/标注 |
| **SoundFont 音源**（GeneralUser GS、FluidR3 等） | ⚠️ 部分含**非商用**条款 | 逐个核对；或引导用户自备音源 |
| **OpenAIR / EchoThief IR** | ⚠️ 学术/CC 混合条款 | 默认用**程序生成 IR**规避 |
| **ML 模型权重**（MusicGen、Stable Audio） | ⚠️ 部分为**非商用**许可 | 引入前必须单独审查；建议先不做 |

> **架构含义**：**数据层与代码层物理分离**。
> `riffle-core`（MIT 代码）不应包含任何音阶数据文件；音阶/框架数据放独立的 `riffle-content` 仓库，各自带 LICENSE，并允许用户自备。

## 5. 项目自身的许可建议

| 选项 | 优点 | 缺点 |
|---|---|---|
| **MIT** | 最宽松、最易被采用、与所有推荐依赖兼容 | 无专利授权条款 |
| **Apache-2.0** | 含**明确的专利授权**与贡献者条款；对企业友好 | 略冗长，需 NOTICE 文件 |
| **AGPL** | 防止他人闭源商用你的网站 | ❌ 会使项目无法使用部分依赖，且与"开放共享"愿景矛盾 |

> **建议：Apache-2.0。**
> 理由：(1) 与 MIT 依赖完全兼容；(2) 含专利授权，对一个可能涉及算法/DSP 的项目更稳妥；(3) 仍允许广泛使用与商业化，符合"开源 + 将来上线"的目标。
> 若追求极简与最大兼容性，**MIT 亦可**——两者对依赖选择无实质差别。

**其余需一并定下**：
- `CONTRIBUTING.md` 中的贡献者许可协议（DCO 或 CLA）
- **代码与数据的许可分离**（代码 Apache-2.0；数据各自许可）
- **用户生成内容的条款**（上线后）：谁拥有用户用 Riffle 生成的作品？建议明确"用户拥有其生成作品"，但需注意这在不同司法辖区对"算法生成内容"的可版权性认定不同
- 第三方声明文件（`THIRD-PARTY-NOTICES`）

## 6. 许可决策清单（实施前逐项打勾）

- [ ] 确定项目主许可（建议 Apache-2.0）
- [ ] 冻结依赖白名单，全部核实 LICENSE 文件（**不依赖 npm `license` 字段，读仓库 LICENSE**）
- [ ] 建立 `THIRD-PARTY-NOTICES`
- [ ] 确认**无 AGPL 依赖被引入浏览器包**（可用 `license-checker` 类工具进 CI 卡口）
- [ ] 音阶/框架数据独立仓库，逐项标注来源与许可
- [ ] 对不可再分发数据，改为"运行时获取 + 用户自备"
- [ ] 上线前审查 UGC 条款与算法生成内容归属
- [ ] CI 中加入许可证扫描（防止将来无意引入 GPL/AGPL）

> **建议的 CI 卡口**：在构建流程中扫描生产依赖树，出现 `GPL`/`AGPL` 即失败。这一条能在未来几年里持续保护项目。
