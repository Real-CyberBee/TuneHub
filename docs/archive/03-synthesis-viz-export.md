# 03 · 音效合成、可视化与导出

> 调研范围：Web Audio 合成技术全景、可视化范式与技术选型、离线渲染与音频/MIDI 导出。
> 本文的 §3 解决主方案里"截断某一段时间保存"这个最需要设计决策的需求。

---

## 1. 音效合成技术全景

### 1.1 按技术分类的实现路径

| 技术 | Web Audio 实现 | 音色特征 | 难度 | 优先级 |
|---|---|---|---|---|
| **减法合成** | Oscillator → Filter → Gain(包络) | 经典合成器、贝斯、pad | 易 | ★★★ |
| **FM / PM** | 一个 Osc 调制另一个的 `frequency` | 钟、电钢、金属、铃 | 易 | ★★★ |
| **加法合成** | 多个 Osc 叠加（或 `PeriodicWave`） | 管风琴、钟、谐波音色 | 易 | ★★★ |
| **波表合成** | `PeriodicWave`（傅里叶系数）/ AudioBuffer 查表 | 复杂/演化的音色 | 中 | ★★ |
| **噪声合成** | AudioBuffer 填随机数（白/粉/棕噪声）→ 滤波 | 打击、风声、镲 | 易 | ★★★ |
| **打击乐合成** | 噪声 + 快速包络 + 音高扫频 | 808/909 风格鼓组 | 易 | ★★★ |
| **粒子合成 (Granular)** | 多个 AudioBufferSource + 随机起点/包络 | 云状、纹理、ambient | 中 | ★★ |
| **物理建模：Karplus-Strong** | 噪声脉冲 → 延迟线 + 反馈 + 低通 | **拨弦（吉他/古筝/竖琴）** | 中 | ★★★ |
| **物理建模：模态合成** | 多个谐振滤波器并联 | 鼓皮、木鱼、金属 | 中 | ★★ |
| **物理建模：波导** | 延迟线网络 | 管乐器 | 难 | ★ |
| **共振峰 / 人声** | 多个带通滤波器模拟共振峰 | 元音、"人声"质感 | 中 | ★★ |
| **采样播放** | AudioBufferSource / `smplr` | 真实乐器 | 易（有库） | ★★★ |
| **SoundFont / SF2** | 解析 SF2 → 采样 + 包络 | General MIDI 音色库 | 中 | ★★ |

### 1.2 具体音效配方（可直接写进代码库）

这不是"随便加个振荡器"，而是**每个音效都要有一份可复现的参数配方**：

| 音效 | 配方 |
|---|---|
| **底鼓 (Kick)** | 正弦，频率从 ~120Hz 指数扫到 ~45Hz，包络 5ms attack / 300ms decay；可选加 `WaveShaper` 饱和 |
| **军鼓 (Snare)** | 白噪声（带通 ~1.8kHz）+ 一个 ~180Hz 正弦"body"叠加 |
| **踩镲 (Hi-hat)** | 白噪声 + 高通 ~7kHz，包络 1ms/50ms（闭）/ 1ms/350ms（开） |
| **拨弦 (Pluck)** | Karplus-Strong：长度 = 1/f 的延迟线，反馈 ≈ 0.99，反馈路径含一阶低通 |
| **钟 (Bell)** | FM：载波/调制比取非整数（如 1:3.5），指数衰减调制指数 |
| **Pad** | 2–3 个失谐锯齿 + 低通（LFO 缓慢扫频）+ 长 attack/release + 立体声展宽 |
| **风/氛围** | 棕噪声 + 带通（LFO 调制中心频率）+ 长包络 |
| **混响** | `ConvolverNode` + IR；无 IR 时可用多重延迟网络近似（Schroeder/FDN） |

> **建议**：把配方做成**声明式数据**（JSON/TS 常量），而不是散落在代码里的命令式调用。这样音效库可以"收集"——正好对应需求 1 —— 且用户能编辑、导出、分享配方。

| 资源 | 许可 | 说明 |
|---|---|---|

## 2. 可视化

### 2.1 音频分析能力

| 需求 | 方案 |
|---|---|
| 时域波形 | `AnalyserNode.getFloatTimeDomainData` |
| 频谱 | `AnalyserNode.getByteFrequencyData`（FFT size 32–32768） |
| 频谱图 (spectrogram) | 逐帧 FFT 累积绘制（自研，轻量） |
| 色度 / 音级轮廓 | 自研：FFT → 频率 → 音级能量折叠 |
| 起音检测 (onset) | 谱通量 (spectral flux) 自研，或用 `meyda` |
| 节拍检测 | `web-audio-beat-detector`（见 04） |
| 音高检测 | 自研 YIN/自相关，或 `pitchy`、CREPE WASM |
| 高级特征 | **`essentia.js`** —— 能力极强，**但 AGPL**，见 04 |

> **重要区分**：本项目**不需要**从音频反推音乐信息来计算音符——因为我们是**生成**音乐，音符在生成时就知道。
> 分析类库主要用途是：(a) 可视化（频谱/波形），(b) **用户输入**（麦克风唱歌 → 音高检测 → 转成事件），(c) 效果器侧链。
> 因此 `essentia.js` 这类重量级 AGPL 依赖**可以完全避免**。这是架构上的一个好消息。

| 范式 | 表达什么 | 技术 | 备注 |
|---|---|---|---|

| **频谱图 (spectrogram)** | 频率×时间×能量 | Canvas2D | ambient 音乐特别有美感 |
| **波形 / 示波器** | 时域 | Canvas2D | |

### 2.4 技术选型权衡

| 方案 | 优势 | 劣势 | 适用 |
|---|---|---|---|
| **Canvas2D** | 简单、命令式、大量图元性能好 | 无 3D、像素化 | **默认**：钢琴卷帘、频谱、音分图 |
| **SVG** | 可选中/可访问/CSS 样式、矢量 | 上千元素后 DOM 性能崩 | 图表、五度圈、控件 |
| **WebGL** | 十万级粒子、shader 效果 | 复杂度高、文本渲染麻烦 | 粒子、3D、氛围视觉 |

**建议**：默认 Canvas2D（demo 已证明可行且轻量）；图表用 SVG/d3；"氛围模式"用 WebGL。**同一份音乐数据（NoteEvent[]）驱动所有视图**——这又一次依赖内核与表现层解耦。

## 3. 导出与离线渲染（关键章节）

### 3.1 离线渲染 vs 实时捕获

| | `OfflineAudioContext` | `MediaRecorder` 实时捕获 |
|---|---|---|
| 速度 | 快于实时（可数倍） | 必须实时等待 |
| 音质 | 确定、稳定 | 受设备负载影响，可能丢帧 |
| 区间控制 | ✅ 任意指定 | ❌ 只能录"正在发生的" |
| 后台运行 | 可嵌套但主线程仍需存活 | ❌ 后台标签页被节流，录音会断 |
| 实现复杂度 | 需要内核支持冷启动 | 低 |
| 可复现 | ✅ 同种子⇒逐样本一致 | ❌ |

> **结论：以离线重渲染为主，实时捕获为兜底。**

### 3.2 离线渲染的实现要点与陷阱

```ts
const ctx = new OfflineAudioContext({
  numberOfChannels: 2,
  length: sampleRate * durationSec,
  sampleRate,
});
// 1) 在 ctx 上构建与实时完全相同的音频图
// 2) 用内核生成 [startSec, startSec+durationSec) 的事件
// 3) 把所有事件时间平移到 0 起点
// 4) ctx.startRendering() → AudioBuffer
```

**陷阱清单**：

| 陷阱 | 后果 | 对策 |
|---|---|---|
| `setTimeout` 调度 | 离线上下文里与音频时钟脱钩，**限流/回收逻辑失效** | **所有调度基于音频时钟**（demo 必须修） |
| `AudioWorklet` 在离线上下文 | 支持情况不一，需等模块加载完成 | 渲染前 `await` worklet 注册；或离线路径用原生节点替代 |
| `AnalyserNode` | 离线渲染中无意义 | 可视化不参与离线路径 |
| 随机性 | 若在渲染时现取随机数，同种子无法复现 | **先在纯内核里生成完整事件表**，再喂给音频图 |
| 时间原点 | 若从作品中间开始渲染，PRNG 状态必须正确 | `prng.stateAt(t)` 或快进 |
| `ConvolverNode` 的 IR | 需提前解码（`decodeAudioData` 是异步） | 预加载并缓存 |
| 内存 | 长时长渲染占用大 | 分段渲染再拼接（注意段边界的尾音/混响） |

### 3.3 编码格式

| 格式 | 库/方案 | 许可 | 备注 |
|---|---|---|---|
| **WAV** | 手写（AudioBuffer → PCM → RIFF） | 无依赖 | **首选**，约 50 行；或 `audiobuffer-to-wav` |
| **MP3** | `lamejs` / `@breezystack/lamejs` | LGPL（lamejs 系需核实） | 普适性最好 |
| **Opus** | `libopus` WASM / `opus-recorder` / `ogg-opus-encoder` | 见 04 | 体积效率最佳，现代浏览器 |
| **FLAC** | `libflacjs` | 见 04 | 无损压缩 |
| **WebM/Opus** | `MediaRecorder` | 浏览器原生 | 仅实时捕获路径 |
| **MIDI** | `@tonejs/midi` / `midi-writer-js` | MIT（需核实） | ⚠️ **标准 MIDI 文件无法表达非 12-TET** |

**WAV 优先**：零依赖、无损、无许可证问题、离线渲染天然产出 AudioBuffer。MP3/Opus 作为可选导出增强。

### 3.4 微分音导出（难点）

标准 MIDI 文件音高是 7-bit 音符号，**无法直接表达微分音**。可用方案：

1. **Pitch Bend 方案**：每个音符前插入 pitch bend 事件，把音高推到目标。
   - 问题：传统 MIDI 通道的 pitch bend 是**全通道**的，复音下互相干扰
   - 缓解：用 **MPE 式多通道分配**（每个音符占一个通道）
2. **MTS (MIDI Tuning Standard)**：SysEx 消息设置音高表
   - 支持度有限（很多软件忽略 SysEx）
3. **MIDI 2.0 Per-Note Pitch Bend**：正解，但生态支持尚不普及
4. **务实方案**：导出时**量化到 12-TET** 并**明确告知用户**损失了什么；同时提供**导出音高表（.scl）+ MIDI** 的组合，让用户在支持的 DAW 里还原

> **建议**：Milestone 4 先做 (4)（诚实降级 + 附带 .scl），(1) MPE 方案作为进阶。

### 3.5 "截断某一段时间保存"的最终方案

这是主方案 §3 需求 ⑤② 的具体实现：

```
用户操作：拖动时间轴选择 [t1, t2] → 点"导出此段"

流程：
1. 序列化当前作品 = (种子, 配置, 起始时间 t1, 时长 t2-t1)
2. 创建 OfflineAudioContext(length = (t2-t1) * sampleRate)
3. 内核以 stateAt(t1) 为 PRNG 起点，生成 [t1, t2+tail) 的事件
   （tail = 混响/尾音时长，避免截断爆音）
4. 事件时间 - t1，喂入离线音频图
5. 渲染 → AudioBuffer
6. 应用淡入淡出包络（10–30ms）避免边界爆音
7. 编码为 WAV/MP3 → 下载
```

**必须处理的细节**：
- **尾音 (tail)**：卷积混响的尾巴可能比 `t2` 长，多渲染 1–3 秒再裁剪
- **边界爆音**：在 `t1` 和 `t2` 应用短淡入淡出
- **进行中的音符**：`t1` 时已开始、`t1` 后仍在响的音符，需要"半途起音"——内核应支持从任意时刻取"活动音符快照"

> 这个"活动音符快照"能力是内核的一个具体设计约束，应当在 Milestone 0 就预留接口。

## 4. 小结

- **合成**：从"配方化的零依赖音效库"起步，AudioWorklet/WASM 留到后期
- **可视化**：以**音分偏差表**为招牌，Canvas2D 为默认，所有视图共享同一事件流
- **导出**：**离线重渲染为核心**，这反向要求内核必须时钟无关、可跳转、可快照——三个约束在 Milestone 0 就要满足
