# 06 · 同类平台调查：网上是否已经存在这样的东西？

> 回答一个立项前最关键的问题：**有人做过吗？做到什么程度？我们还有空间吗？**
> 结论先给：**没有任何一个产品覆盖你的完整构想，而且缺的恰好是最难的那几块。**
> 但有几个项目在**单点上**非常接近，必须认真研究。

---

## 0. 结论速览

把你的构想拆成 6 个能力，对照现有项目：

| # | 能力 | 现有最佳 | 覆盖度 |
|---|---|---|---|
| 1 | WebAudio 音效合成收集 | Tone.js 生态、SoundFont 库 | ✅ **已充分解决** |
| 2 | 随机音乐生成（可玩、零门槛） | 大量玩具 + generative.fm | ✅ **已充分解决** |
| 3 | **多种律制/音阶体系可玩** | Scale Workshop、Apotome/Leimma | ⚠️ **部分解决，但偏工具** |
| 4 | **拉格/木卡姆/甘美兰的"框架"建模** | Digital Arabic Maqām Archive | ⚠️ **个别体系有，无通用平台** |
| 5 | 丰富可视化 | 各自散落 | ⚠️ **无跨体系统一方案** |
| 6 | **社区可贡献内容（音阶/风格/可视化）** | generative.fm（**但拒绝 PR**） | ❌ **基本空白** |

**关键发现**：第 2 项（随机生成）竞争激烈且已饱和；第 6 项（可贡献的平台）几乎空白——而你的架构恰好把重心放在 6，同时用 3+4 做差异化。

---

## 1. 最需要认真对待的三个项目

### 1.1 generative.fm —— 形态最接近，但**主动拒绝社区贡献** ★最重要

| | |
|---|---|
| 定位 | "A platform for playing generative music in the browser" |
| 开源 | 是（GitHub `generativefm/generative.fm`） |
| 现状 | 有学术论文（WAC 2019）、有 Patreon、有精选艺术家作品 |

**它的 CONTRIBUTING.md 是一手材料，也几乎是给我们写的反面教材。** 维护者 Alex Bainter 明确写道：

> "**for the time being it's unlikely I will be accepting any outside pull requests.**"

给出的理由有两条，**恰好对应你要解决的问题**：

1. **"想要绝对的创作控制权"**——"我平时在团队里写代码，做个人项目就是为了不受他人需求约束"
2. **安全问题**——被问"我也做浏览器生成音乐，能加到你站上吗"，回答是：
   > "The site is designed to accomodate other artists, **but integrating your code is a security risk for me** and I'm not sure I'm up for it right now."

**它甚至直接喊话**：
> "If you have a better idea for a generative music platform, I'm all ears."

**对我们的三点启示**：

| 教训 | 我们的对策 |
|---|---|
| 架构上"支持多艺术家"≠ 实践中"敢接受贡献" | **贡献主形态必须是数据**（数据无代码执行风险）。这正是 `05-platform-architecture.md` 的核心论点，现在有了实证支撑 |
| 安全是社区平台的真障碍，不是借口 | 数据包与代码包走**两条信任路径**；可视化代码沙箱隔离 + 性能预算 |
| 单人维护者的控制欲会扼杀平台 | 需要**治理机制**：策展列表、明确的内容等级、贡献者署名（见 `05` §6） |

> **战略含义**：generative.fm 证明了"生成音乐平台"这个形态**有受众、有学术认可**，同时也证明了**如果不解决贡献门槛与安全，平台会退化成单人作品集**。这是我们可以明确超越的地方。

### 1.2 Scale Workshop —— 律制领域的"事实标准工具"，但**不是平台**

| | |
|---|---|
| 定位 | 浏览器内设计微调音阶，导出给 VST 使用 |
| 开源 | 是（xenharmonic-devs；历史上经手多人，有多个 fork） |
| 技术 | 其语言内核即 **sonic-weave**（MIT，我们已选定复用） |
| 周边 | Xenharmonic Wiki 有专门条目；有用户手册 |

**它做了**：音阶设计、试听、导出（Scala 等格式）、显示音程与音分。
**它没做**：生成音乐、节奏与织体、可视化艺术性、风格配方、游戏化、社区内容策展。

**它是"工具"，我们要做"平台 + 玩法"。** 关系是**互补而非竞争**：它的音阶可以成为我们的内容来源，它的交互范式值得学习（尤其是"直接看到音分数字"这一点，正是我们的招牌可视化）。

### 1.3 Apotome & Leimma（Khyam Allami / Counterpoint）—— 最接近的"理念同行"

| | |
|---|---|
| 定位 | 面向**阿拉伯与中立音体系**的浏览器工具（Apotome 做音阶探索，Leimma 做律制比较） |
| 背景 | 有正经的学术与出版背景（Khyam Allami 是知名阿拉伯实验音乐人） |
| 相关 | 同一脉络下还有 **Digital Arabic Maqām Archive + 开源 MIDI 插件**（AUB 音乐智能实验室） |

**它做了**：把"非 12-TET 的音高体系"变成可听可玩的浏览器工具，且带明确的**去殖民化音乐技术**立场——正是你要做的第 3、4 项。

**它没做**：通用平台（不自称支持任意律制家族）、生成式玩法、社区内容库、多形态游戏。

> **这是你的项目在"价值观"上最接近的先行者。** 建议认真研究它的音高交互与措辞，并在文档中引用它。**它不是竞争对手，而是可以结盟/引用的同路人**——这能极大提升项目的学术可信度。

## 2. 其他相关项目（按类别）

### 2.1 零门槛音乐玩具（第 2 项：已饱和）

| 项目 | 开源 | 与我们的关系 |
|---|---|---|
| **Chrome Music Lab**（Google） | 部分开源（googlecreativelab 有仓库） | **最佳教学交互范本**。把抽象概念变成可玩控件 |
| **Blob Opera** | 否（有非官方增强版） | 用生物隐喻降低门槛；闭源但交互值得学 |
| **Musical Toys** | ⚠️ 见下 | "一堆音乐小玩具的集合"——**与"多形态小游戏"最接近的现成产品** |
| **Musical Spirograph** | **否**（The Verge 报道，明确闭源） | 画图生成音乐，视觉极美 |
| **Incredibox / Sprunki** 系 | 否（商业） | 拖拽音效循环的组合玩法；**验证了"音乐小游戏"的市场** |
| **Elemental Musical Adventures** | 否 | 儿童音乐创作 |

**⚠️ Musical Spirograph 的教训**：The Verge 报道它是"soothing, hypnotic"的浏览器生成音乐玩具，但**代码不开放**。这正说明：**好看的生成音乐玩具要么闭源，要么几个人做**——你要做的开源平台是有生态位的。

| 项目 | 关系 |
|---|---|

| **Orca** | 网格即程序，MIT。**交互范式范本** |

| **Bulka** | Strudel 的浏览器 fork，带 AI 与社区（俄语）。**说明"Strudel 平台化"已有人尝试** |
| **ComposeYogi** | "开源版网页 Ableton"。**传统 DAW 形态**，与我们的理念相反（我们不做 DAW） |

### 2.3 AI 音乐生成（不同赛道）

| 项目 | 关系 |
|---|---|

## 3. 那么，你的位置在哪里？

### 3.1 空白点（无人覆盖）

**没有任何一个开源项目同时做到：**

1. 把**律制 → 音阶 → 框架**三层都建模，且**框架层**（拉格 `pakad`、木卡姆 `seyir`）是通用可扩展的数据结构 ← **最硬的技术差异化**
2. 让社区**主要靠写数据**来贡献音阶/风格/可视化
3. 以**多种玩法形态**（游戏/画布/教学）消费同一套音乐内核
4. 把**出处与近似程度**（`provenance`）做成强制的数据结构

### 3.2 但也有真实风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| **"又一个生成音乐玩具"** | 第 2 项已饱和，用户可能不觉得新的有什么不同 | **必须在前 30 秒展示律制差异**（音分偏差可视化），这是别人没有的"啊哈时刻" |
| **律制工具已有强者** | Scale Workshop / Apotome 在各自细分领域很深 | 不正面竞争"音阶编辑器"，而是**做它们的下游**：把音阶变成音乐 |
| **贡献者从哪来** | generative.fm 的教训说明这最难 | 浏览器内编辑器（M2）+ 数据化贡献 + 署名激励 |
| **学术可信度** | 做世界音乐容易被批评"肤浅/挪用" | 强制 `provenance` + 明确的"不做"清单 + 引用 Apotome 等同路人 |
| **单人维护可持续性** | generative.fm 的另一个教训 | 从第一天就设计治理与策展，而非事后补 |

### 3.3 建议的差异化定位（一句话）

> **不是"又一个随机音乐生成器"，也不是"又一个音阶编辑器"，而是"把世界各地的音高体系变成可以玩、可以贡献、可以出题给游戏的开放式实验室"。**

三个不可替代的价值：
1. **能听见差异** —— 音分偏差可视化 + 同旋律跨律制 A/B（现有玩具做不到）
2. **能贡献而不用写代码** —— 音乐学者可以只写 JSON（现有平台做不到）
3. **能玩而不只是调参** —— 游戏作为内核一等消费者（现有项目没这么设计）

## 4. 应当立即做的三件事

1. **精读 generative.fm 的 CONTRIBUTING.md 与它的架构**——它是最接近的先例，其失败之处（拒绝贡献、安全顾虑）正是我们的设计输入。
2. **精读 Apotome/Leimma 的交互与措辞**，并考虑主动联系/引用（同路人，能提升可信度）。
3. **验证 Scale Workshop 的音阶能否作为我们的内容来源**（许可 + 格式），这能一夜之间获得大量音阶内容。

## 5. 诚实交代

- 本文基于**有限轮次**的网络检索（`web_search` 与 `web_fetch` 本轮多次失败）。**几乎可以肯定存在遗漏**，尤其是非英语项目、学术项目、以及已停止维护的早期实验。
- 已一手核实：`generative.fm` 的 CONTRIBUTING.md（已读全文）、`sonic-weave` 与若干 npm 包许可。
- 未逐项核实：各项目的当前活跃度、星数、最新版本；`Musical Toys` 的开源状态；`Scale Workshop` 各 fork 的现状与许可；`Digital Arabic Maqām Archive` 的插件许可证。
- **建议**：立项前用 `awesome-webaudio`（`notthetup/awesome-webaudio`）与各相关 GitHub 话题页做一次穷尽式扫描，本文可作为扫描的起点与分类框架。
